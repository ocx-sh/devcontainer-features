# Friction log: T05 make ocx work for a user other than the installer (status quo, no feature yet)

## Context

A platform developer who has never used ocx, with a container that builds as root and runs
as a non-root user named `dev`, the usual Dev Containers split. They install ocx during the
image build with the official one-liner, as every Dockerfile example does, and expect the
`dev` user to run it. Run on 2026-11-17 against ocx 0.6.8 on `alpine:3` with Docker 29.9.3.
Written by the planning agent with the repository in context, not by a subagent without it.
The feature does not exist, so this is the behaviour the feature must replace.

## Pros and cons

- Good: the root install itself succeeded and exited 0.
- Bad: the `dev` user got no `ocx` at all, because the installer wired the profile of the user who ran it.
- Bad: the store directory `/root/.ocx` is not readable by `dev`, so copying the path from the install output is no workaround.
- Predicted, not observed: a `containerUser` that differs from `remoteUser`, and a missing `_REMOTE_USER`, add two more variants of the same confusion.

## Detailed stream of consciousness

Installed as root, then checked as `dev`.

```text
$ docker run --rm alpine:3 sh -c 'apk add -q curl >/dev/null 2>&1; adduser -D dev; curl -fsSL https://setup.ocx.sh/sh | sh >/dev/null 2>&1; echo root-install-exit=$?; su dev -c "command -v ocx || echo ocx-not-on-PATH-for-dev; ls -ld /root/.ocx"'
root-install-exit=0
ocx-not-on-PATH-for-dev
ls: /root/.ocx: Permission denied
```

The install claimed success and the intended user has nothing. I would now search for how to
install for another user, and the installer page says nothing about it. The only fix I can
see is to rerun the installer as `dev`, which an image build cannot do cleanly.
