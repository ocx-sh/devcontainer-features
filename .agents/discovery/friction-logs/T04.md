# Friction log: T04 restore the project toolchain in a fresh container (observed commands, no feature yet)

## Context

A developer who has never run ocx in a project, who has just cloned a repository and wants
the declared tools restored by a container lifecycle hook. The hook command is the one the
ocx documentation names for dev containers (`ocx pull`). Run on 2026-11-17 on the host with
ocx and an empty `OCX_HOME`. Written by the planning agent with the repository in context,
not by a subagent without it. Whether `ocx env` auto-installs before `ocx pull` ran, and how
the VS Code extension behaves in a remote window, were not run: predicted, not observed.

## Pros and cons

- Good: both failure cases print the exact next command to run.
- Bad: a repository without `ocx.toml` makes the hook command exit 64, so an unguarded hook fails container creation for every project that does not use ocx.
- Bad: a repository with `ocx.toml` and no `ocx.lock` exits 78. The feature's docs must say whether the container still starts, and the reader must know the fix is `ocx lock` on a machine with network.
- Predicted, not observed: the first terminal does not activate the toolchain until consent exists; the feature sets a consent path for the workspace folder, and that default is the part a reader will question.

## Detailed stream of consciousness

exit=64

The first project I tried had no `ocx.toml`. A hook that runs this unguarded would break the
container for everyone. Then a project with `ocx.toml` but no lock.

```text
$ ocx pull
error: ocx.lock not found at /tmp/tmp.uHDdMMQH3W/ocx.lock; run `ocx lock` to create it: ocx.lock not found at /tmp/tmp.uHDdMMQH3W/ocx.lock; run `ocx lock` to create it
exit=78
```

The message repeats itself, but the next action is clear. What I cannot tell from the output is
whether a failed restore should stop the container from starting. That answer has to be on
the page.
