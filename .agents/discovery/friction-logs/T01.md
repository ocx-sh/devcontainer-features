# Friction log: T01 and T06 get ocx into a bare container image (status quo, no feature yet)

## Context

A backend developer who has never installed ocx, working in a plain `alpine:3` image and a
plain `debian:stable-slim` image. Their only instruction is the official one-line installer
(`https://setup.ocx.sh/sh`). This is the path a user takes today because the feature does not
exist. Run on 2026-11-17 against ocx 0.6.8 with Docker 29.9.3. Written by the planning agent
with the repository in context, not by a subagent without repository access, so the
"first time" persona is a stance, not a measurement. Items marked "predicted, not observed"
were not run.

## Pros and cons

- Good: on Alpine the installer needs no extra package. The BusyBox `wget` path worked and ended with "ocx 0.6.8 installed successfully!".
- Bad: after a successful install as a non-root user, `ocx` was not on PATH in the same shell. The message says "Restart your shell". A container build never restarts a shell.
- Bad: on Debian slim the installer fails because `curl` is missing, and the shell reported exit 0 for the pipeline. A Dockerfile `RUN` line would pass.
- Bad: the installer wrote five shell profile files and a systemd environment file in the user's home. A reader building an image does not expect that.
- Predicted, not observed: on `busybox`, `ubi-minimal` and `wolfi-base` the same pipeline fails on a missing `tar` or CA bundle with a message the reader cannot map to a package name.

## Detailed stream of consciousness

Started with Alpine as a non-root user, using the documented one-liner with `wget` because `curl` is absent.

```text
$ docker run --rm alpine:3 sh -c 'adduser -D dev && su dev -c "wget -qO- https://setup.ocx.sh/sh | sh; echo exit=\$?; command -v ocx || echo ocx-not-on-PATH; ls -a ~ | head"'
              /home/dev/.bashrc (completed)
              /home/dev/.zprofile (completed)
              /home/dev/.zshrc (completed)
Session PATH  /home/dev/.config/environment.d/ocx.conf (written)

  ocx 0.6.8 installed successfully!

  Restart your shell, then verify with:

    ocx about

exit=0
ocx-not-on-PATH
.
..
.bashrc
.config
.ocx
.profile
.zprofile
.zshrc
```

It worked, but I cannot type `ocx` yet. In an image build there is no "restart your shell",
so I would have to guess the path under `~/.ocx/symlinks/...`.

Then Debian slim, which has no `curl`, with the same one-liner.

```text
$ docker run --rm debian:stable-slim sh -c 'curl -fsSL https://setup.ocx.sh/sh | sh; echo exit=$?'
sh: 1: curl: not found
exit=0
```

The installer never ran. Because the last command of the pipeline is `sh` reading an empty
script, the pipeline exits 0. A CI step or a Dockerfile `RUN` would report success and fail
only later, at the first `ocx` call.

I did not try the remaining images. That part stays predicted, not observed.
