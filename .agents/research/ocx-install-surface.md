## 1. Official install method

**One-liner.** `curl -fsSL https://setup.ocx.sh/sh | sh` (`DOCS/getting-started/install-ocx.mdx:16-18` renders the picker; the literal strings are pinned in `/home/mherwig/dev/ocx-sh/website/site/src/install.test.ts:8-14`). One script per shell: `/sh` (POSIX), `/pwsh`, `/nu`, `/fish`, `/elvish` (`DOCS/guides/install-options.mdx:20,169-177`). Version-pinned immutable URL: `https://setup.ocx.sh/sh/0.5.0` (`install-options.mdx:99-107`). `https://ocx.sh/install*` is only a redirect target (`/home/mherwig/dev/ocx-sh/website/infra/bunny/__snapshots__/plan-prod.json:435-439`; `curl -sI https://setup.ocx.sh/` answers 302 to `https://ocx.sh/install/`).

**Source of truth.** Repo `https://github.com/ocx-sh/www-setup`, files `src/install.{sh,ps1,nu,fish,elv}` (git tree listing, `gh api repos/ocx-sh/www-setup/git/trees/HEAD`). Not in the `ocx` repo (its `.claude/skills/installer-script/references/install-template.sh` is only a template). Rules the installer is held to: `/home/mherwig/dev/ocx-sh/ocx/.claude/rules/shell-quality/installers.md` (SH-INST-01..23: truncation guard, fail-closed sha256, `--proto '=https'`, exit table 0-7, no sudo, `--no-modify-path`).

**Dialect.** POSIX `sh` plus a probed `local` (`INST:5`, `INST:32-34`). Shebang `#!/bin/sh` (`INST:1`). Written to run under dash, busybox ash, bash, zsh. Truncation-safe: only function defs at top level, ends `main ${1+"$@"}` (`INST:1022`). The tool header says "THIN BOOTSTRAP" (`INST:12-18`): it detects the platform, downloads and verifies the archive, then runs `ocx self setup`.

**Required tools** (all checked, else exit 2): `uname`, `mktemp`, `tar` (`INST:872-874`); `curl` or `wget` (`INST:334-357`; curl preferred, `OCX_INSTALL_DOWNLOADER=curl|wget` forces); one of `sha256sum`, `shasum`, `openssl` (`INST:471-481`); also uses `awk`, `sed`, `grep`, `head`, `tr`, `basename`, `dirname`, `cat`, `sleep`, `rm`, `cp`, `chmod`, `mkdir` (all present in busybox). `getent` + `cut` only if `$HOME` is unset (`INST:168-178`). `ldd` is optional (loader-file fallback, `INST:257-284`). `tput` optional (`INST:181-187`). Needs `ca-certificates` for curl's own TLS (curl uses the system store; unlike `ocx`, see topic 3). wget handling: GNU wget >= 1.17 (older rejected, `install-options.mdx:26-28`); BusyBox wget warns and refuses an unpinned manifest if it reports "certificate validation not implemented" (`INST:386-388,428-434,605-610`). **[tested]** alpine:3 (BusyBox wget + BusyBox tar, no curl) installs fine; debian:stable-slim (no curl/wget) exits 2 `either curl or wget is required to download OCX`.

**Flags** (`INST:213-250`, parsing `INST:782-800`): `--version <V>` / `--version=V`, `--no-modify-path`, `-h/--help`. Unknown flag exits 2. Pass via `sh -s -- <flags>` (`install-options.mdx:32-39`).

**Env vars** (`INST:70-125`, usage text `INST:228-249`):

| Variable | Effect |
|---|---|
| `OCX_HOME` | install root, default `$HOME/.ocx`; must be absolute, no `..`, no shell metacharacters (`INST:706-726`, exit 2) |

| `OCX_MANAGED_CONFIG` | corporate managed-config OCI ref, read by `ocx self setup` |
| `OCX_INSTALL_VERSION` | pin; empty = latest stable (never a prerelease, `install-options.mdx:127`) |

| `OCX_INSTALL_NO_SETUP` | truthy = place binary only, skip `ocx self setup` (`INST:988-990`) |

Truthy values for installer knobs: `1 true yes TRUE YES True Yes` (`INST:101-106`).

**What it writes.**
- Default mode: downloads the archive to `mktemp -d`, runs the downloaded binary as `ocx self setup <version>`. That pulls `ocx.sh/ocx/cli` from the registry into the content-addressed store under `$OCX_HOME` and wires `$OCX_HOME/symlinks/ocx.sh/ocx/cli/current/content/bin/ocx` (`INST:189-190`, `INST:996-1003`; `install-options.mdx:183-192`). It writes `$OCX_HOME/env.{sh,fish,ps1,nu,elv}`, adds a fenced managed block to each detected shell profile of the installing user, and writes session PATH registrations (Linux: `~/.config/environment.d/ocx.conf`) (`install-options.mdx:20-22,185-190,245-272`). `ocx self setup` therefore needs registry network access too (`install-options.mdx:192`: "If the bootstrap fails, for example because the registry is unreachable ... writes nothing"). **[tested]** alpine root: `/root/.ocx/{blobs,index,layers,locks,packages,state,symlinks,temp,env.*}`, `/root/.profile` managed block `# >>> ocx v1 0fe65b70 >>>` sourcing `${OCX_HOME:-$HOME/.ocx}/env.sh`. Dirs 0755, `env.*` files 0600, binary in the store is 70 MB.
- `OCX_INSTALL_NO_SETUP=1`: only `mkdir -p $OCX_HOME/symlinks/ocx.sh/ocx/cli/current/content/bin; cp ocx` there (`INST:674-680`). No registry call, no profile edit, no session PATH. `ocx self update` will not manage such an install (`INST:671-673`). **[tested]** with `OCX_HOME=/usr/local/share/ocx OCX_INSTALL_NO_SETUP=1 OCX_INSTALL_VERSION=0.6.8` on alpine:3: rc 0, only `/usr/local/share/ocx/symlinks/...` created, `/root/.profile` untouched.

**Integrity.** Archive sha256 comes inline from `dist.json` served by `setup.ocx.sh`, a different origin from GitHub (header `INST:7`; verify `INST:495-511`; fail closed: no hash tool exit 2, malformed digest exit 3, mismatch or empty exit 4; `INST:471-481,934-941`). TLS: `curl --proto '=https' --tlsv1.2` (when probed), 3 attempts with 1s/2s backoff (`INST:396-465`), non-https URL refused exit 3 (`INST:327-332`). Archive extraction scanned for `..`, absolute paths, escaping links before `tar xf` (`INST:522-557`). Not signed at archive level: only `sha256.sum`/`*.sha256` exist as release assets (topic 2). Sigstore signature + CycloneDX SBOM exist for the OCI package `ocx.sh/ocx/cli`, verifiable with `ocx package verify` (`install-options.mdx:363-393`, `/home/mherwig/dev/ocx-sh/ocx/.github/workflows/release.yml:235,330`). The installer does not check them.

**Exit codes** (`INST:6`): 0 ok, 1 generic, 2 usage/env/missing tool, 3 network, 4 checksum, 5 extract, 6 setup (`ocx self setup` failed), 7 platform (not Linux/macOS, arch not x86_64/aarch64, or glibc-vs-musl undecidable), 129/130/143 HUP/INT/TERM.

**Stdout/stderr.** Everything to stderr; stdout silent unless `OCX_INSTALL_PRINT_PATH` (`INST:25-28`).

**Docs-recommended non-script route** (`DOCS/getting-started/install-ocx.mdx:33-96`): download the archive, `sha256sum --check --ignore-missing sha256.sum`, extract, run `ocx self setup`. For containers the project documents a third route: copy the static binary into `/usr/local/bin/ocx` (topic 6).

## 2. Release artifacts

Release assets of v0.6.8 (`gh release view -R ocx-sh/ocx`): `ocx-<triple>.tar.gz` (+ `.sha256` each) for `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`; `ocx-{x86_64,aarch64}-pc-windows-gnullvm.zip` (+ `.sha256`); plus `sha256.sum`, `dist-manifest.json`, `ocx.cdx.xml`. Documented at `DOCS/getting-started/install-ocx.mdx:39-50,111-118`.

- **Naming/URLs:** `https://github.com/ocx-sh/ocx/releases/download/v<VER>/ocx-<triple>.tar.gz`; "latest" alias `https://github.com/ocx-sh/ocx/releases/latest/download/<asset>` (HTTP 302 to `.../download/v0.6.8/...`, confirmed with `curl -I`). Tag is `v<semver>`. The installer instead resolves the version from `https://setup.ocx.sh/dist.json` (`INST:613-628`, "no GitHub API"). `dist.json` schema: `{"schema":1,"latest":{"version","channel"},"latest_next":null,"releases":[{"version","channel","tag","target","filename","sha256","url"}]}` (fetched; `INST:561-570`). Prerelease channel `latest_next` (null today).
- **Archive layout** (verified by extracting both Linux x86_64 archives): top dir `ocx-<triple>/` holding `ocx`, `LICENSE`, `LICENSE-THIRD-PARTY.md`, `README.md`, `CHANGELOG.md`. Installer accepts nested or flat (`INST:959-967`).
- **Checksums:** `sha256.sum` in `<hex> *<file>` form (fetched, `curl .../sha256.sum`) and per-archive `<archive>.sha256`. No GPG, no cosign on the archives. `setup-ocx` verifies the `.sha256` sidecar (same origin) (`https://github.com/ocx-sh/setup-ocx` `src/download.ts`).
- **Linkage, verified on the v0.6.8 x86_64 archives:** `-musl` = `ldd`: "statically linked" **[tested]** (also documented fully static: `DOCS/guides/install-options.mdx:202-204`, `DOCS/integration/docker.mdx:58`). `-gnu` = dynamic, `NEEDED`: `librt`, `libpthread`, `libm`, `libdl`, `libc.so.6`, `ld-linux-x86-64.so.2`; highest versioned symbol `GLIBC_2.28` (objdump). Release gate: no `GLIBC_` above 2.34 and a `NEEDED` allow-list (`/home/mherwig/dev/ocx-sh/ocx/scripts/release_provenance_check.py:66-69,73-`; `.github/workflows/scan-binaries.yml:13-16`). So the documented minimum for `-gnu` is glibc 2.34 worst case, 2.28 measured on x86_64 0.6.8; aarch64-gnu not measured.
- **TLS stack:** rustls (`reqwest ... features = ["rustls"]`, `Cargo.toml:142`), `webpki-root-certs` compiled in (`Cargo.toml:145`); no OpenSSL. **[tested]** the musl binary pulled from `ocx.sh` on `busybox:1.37-musl` (no `/etc/ssl`) and on `debian:stable-slim` (no `/etc/ssl/certs`), no CA package needed.
- **musl is what the OCI package ships:** release `PLATFORMS` for the self-install package are `linux/amd64` and `linux/arm64` built from the `*-unknown-linux-musl` triples (`release.yml:67-73`), so `ocx self setup` on a glibc host also installs the static build.
- **Feasibility:** the musl archives run on any x86_64/aarch64 Linux regardless of libc. **[tested]** alpine:3 and debian:stable-slim and busybox:1.37-musl (rc 0, `ocx version` = 0.6.8). The installer picks `gnu` vs `musl` by evidence (`ldd --version` text, `/lib/ld-musl-*.so.1`, `/etc/alpine-release`, then `ld-linux*` files, else exit 7) (`INST:257-284`); it never picks musl on a glibc host. Unsupported by any route: 32-bit (`i686`, `armv7`), `riscv64`, `ppc64le`, `s390x` (`INST:295-300` exit 7).

## 3. Runtime requirements inside a container

- **Env/dirs.** `OCX_HOME` (else `~/.ocx`) is the only data root (`DOCS/reference/environment.md:229-242`). `ocx about` shows `Home`. **[tested]** with `HOME` unset and `OCX_HOME=/tmp/o` as uid 1000 on busybox:1.37-musl: `ocx package pull` works, creating `blobs index layers locks packages temp` under it. Writes needed: `$OCX_HOME` (store, index, locks, temp), the project dir for `.ocx/toolchain/` and `ocx.lock`. `toolchain_dir`/`OCX_TOOLCHAIN_DIR` relocate the rendered toolchain (`environment.md:710-718`). System config optional at `/etc/ocx/config.toml` (`DOCS/explanation/configuration.mdx:32-41,203-218`); `OCX_INDEX` swaps the index for a shipped copy ("meant for ... devcontainer", `environment.md:259-272`; `DOCS/explanation/indices.md:34,80-88`).
- **Container-relevant env knobs:** `OCX_NO_UPDATE_CHECK=1` (the official images bake it in, `DOCS/integration/docker.mdx:20`; also off when `CI` truthy or stderr not a tty, `environment.md:512-524`); `OCX_NO_CONSENT=1` for images/pipelines (`environment.md:450-463`, `DOCS/integration/unattended-ci.mdx:34-44`); `OCX_CONSENT_PATHS=/workspaces/*` lets a devcontainer activate a checkout without a stamp (`environment.md:164-173`; unit test `crates/ocx_config/src/shell.rs:1415-1425` names exactly this use); `OCX_OFFLINE`, `OCX_FROZEN`, `OCX_JOBS`, `OCX_EXTRA_CA_CERTS`, `OCX_AUTH_<REGISTRY>_{TYPE,USER,TOKEN}` (`environment.md:72-105,188-215`, `docker.mdx:93-111`).
- **Root vs non-root.** No privilege requirement; **[tested]** works as root and as uid 1000. Everything is per-user by default (`~/.ocx`). The `ocx self setup` profile block and env files are written only for the user who ran it (root at feature build time), and `env.*` are mode 0600 (**[tested]**), so a root-run `self setup` does not give `remoteUser` a working hook.
- **System-wide binary, per-user store:** supported and the project's own documented container pattern: `COPY --from=ghcr.io/ocx-sh/ocx:<ver>-alpine /usr/local/bin/ocx /usr/local/bin/ocx` (`docker.mdx:50-58`, `DOCS/integration/devcontainers-and-editors.mdx:67-72`). **[tested]** a bare `/usr/local/bin/ocx` runs for any user with a private `OCX_HOME`.
- **Shared `OCX_HOME` between root and `remoteUser`:** not documented. **[tested]** a root-created `OCX_HOME=/opt/ocx` is unusable by another user as created (`ocx --offline package exec` as uid `u`: `internal file error for '/opt/ocx/index/ocx.sh/config.json': Permission denied`), and works after `chmod -R a+rwX /opt/ocx` (`package exec` and `init/add/pull/exec` as `u`). Store files are created with default umask, index files 0600; a group-writable setup would also need a matching umask/group. Treat a shared store as unsupported-but-workable.
- **Network/registry.** Default registry `ocx.sh` (`environment.md:175-186`, `OCX_DEFAULT_REGISTRY`); `ocx pull` fetches digest-pinned blobs from the registry that hosts them (packages are `ocx.sh/...` logical names, physical home `ghcr.io/ocx-sh/...`, `release.yml:33-36`). Index metadata comes from `index.ocx.sh`-style static hosting; proxy via `HTTP(S)_PROXY`/`ALL_PROXY` (`environment.md:838-`), mirrors in `[mirrors]` (`DOCS/guides/corporate-mirror.mdx`), corporate CA via `OCX_EXTRA_CA_CERTS` (`DOCS/integration/proxy-and-ca.mdx`). `--offline`/`--frozen` for build-time pull + run-time offline (`docker.mdx:78-91`).
- **External binaries at runtime:** none required for install/pull/exec. Archive layers (tar+xz/zstd/gz, zip) are decoded in-process (`Cargo.toml:213-231`); the only `Command::new` spawns in non-test code are shell detection probes in `crates/ocx_shell/src/shell.rs` and `hook.rs`. No git, no tar.
- **Not signed packages by default:** `ocx pull` logs "no trust policy covers 'ocx.sh/...'; installing ... without signature verification" (**[tested]**).
- **Platform selection:** the platform string carries libc features (`linux/amd64+libc.glibc`, `+libc.musl`); `-p` overrides (`ocx pull --help`). **Package availability differs by libc** (topic 5): `nodejs/node` is glibc-only, so it will not install on Alpine.

## 4. Shell integration and the post-clone toolchain flow

**Commands** (`ocx --help`, `ocx self --help`, `ocx shell --help`; `DOCS/explanation/shell-integration.mdx`):
- `ocx self setup [VERSION] [--no-modify-path] [--no-profile] [--profile PATH]... [--completion|--no-completion] [--hook|--no-hook] [--toolchain-activate env|bin|none] [--dry-run] [--force]` writes env files, profile blocks, session PATH, installs ocx into the store. Registry required (`ocx self setup --help`).
- `ocx self activate --shell[=bash|zsh|fish|ash|dash|ksh|sh|pwsh|elvish|nushell|batch]` is what `$OCX_HOME/env.sh` calls: prepends `$OCX_HOME/toolchain/active/bin` and the ocx bin dir to PATH, injects completions (skipped when non-interactive or `OCX_NO_COMPLETION=1`), evaluates the global toolchain env.
- `ocx shell completion --shell bash|zsh|fish|elvish|powershell [--if-enabled]` prints a completion script (`ocx shell completion --help`).
- `ocx env --shell=<name>` prints eval-safe export lines for the project toolchain (bash zsh dash ash ksh fish elvish powershell nushell batch); `ocx env --ci=github|gitlab` writes to the CI channel (`ocx env --help`). The project-toolchain recipe for devcontainers uses `eval "$(ocx --offline env --shell=bash)"` (`devcontainers-and-editors.mdx:76-84`).
- `ocx shell` opens a subshell in the project environment; `ocx shell allow|revoke|state`; `ocx exec [-g GROUP] -- cmd` runs a command in the composed environment (alias `x`); `ocx direnv init|export`; `ocx --format json shell state | jq -r .toolchain_bin` gives the directory holding launchers for every tool (`devcontainers-and-editors.mdx:30-61`); `ocx_cli/src/api/data/shell_state.rs:247` names devcontainer features as the intended consumer of `toolchain_home`.
- The prompt hook activates a *consented* project at the next prompt; a fresh clone stays inert until a consent stamp or grant (`shell-integration.mdx:15-33,152-168`). `ocx init|add|remove|lock|update|upgrade|pull|exec` stamp consent as a side effect unless `OCX_NO_CONSENT`/`--no-consent`.

**Project files.** `ocx.toml` (`#:schema https://ocx.sh/schemas/project/v1.json`, `[tools]` table `name = "ocx.sh/<org>/<pkg>:<tag>"`, optional `[group.<name>]`), `ocx.lock` (per-platform digests; `lock_version = 4` in this repo, generated by 0.6.8), rendered toolchain at `<project>/.ocx/toolchain/{links,shells,active -> shells/default}` with its own `.gitignore` (`ocx pull --help`; this repo's `.ocx/` has exactly that tree). This repo: `/home/mherwig/dev/ocx-sh/devcontainer-features/ocx.toml` = `node = "ocx.sh/nodejs/node:26"`, `shellcheck = "ocx.sh/shellcheck/shellcheck:0.11"`, `task = "ocx.sh/go-task/task:3"`; `ocx.lock` records digests for darwin, linux (node: only `linux/*+libc.glibc`), windows. `grimoire.toml` is a separate tool (agent bundles), unrelated to ocx. `ocx.toml` is found by walking up from CWD (stops at first `.git` or `OCX_CEILING_PATH`, `environment.md:122-133`).

**Post-clone command for `postCreateCommand`: `ocx pull`** (`ocx pull --help`; `docker.mdx:76`; `devcontainers-and-editors.mdx:79`). It downloads the digest-pinned `ocx.lock` entries of the default group (`-g all` or `-g <g>` for others, `-p os/arch+libc.x` to override platform), then renders `.ocx/toolchain`. Needs both files (`ocx pull` on a stale lock exits 65, missing lock exits 78, `unattended-ci.mdx:46-52`). There is no `ocx install`/`sync` at project level (`ocx package install` is the no-`ocx.toml` form). To run tools: `ocx exec -- <cmd>` (hermetic), or put `$(ocx --format json shell state | jq -r .toolchain_bin)` on PATH, or `eval "$(ocx --offline env --shell=bash)"` in `~/.bashrc`/`~/.zshrc`. Pipeline form: `ocx lock --check && ocx --frozen pull && ocx --offline exec -- <cmd>` (`unattended-ci.mdx:50-60`). **[tested]** `ocx init; ocx add jqlang/jq:1.8; ocx pull; ocx exec -- jq --version` as non-root with `OCX_HOME` set: prints `jq-1.8.2`, creates `ocx.toml`, `ocx.lock`, `.ocx/toolchain`.

## 5. Adding tools; availability

**Add syntax** (`ocx add --help`): `ocx add [-g GROUP] [--no-pull] [-p PLATFORM] <[NAME=]IDENTIFIER>...`. Needs an existing `ocx.toml` (`ocx init` creates one; `ocx add` never creates it, exit 64). The identifier may be bare (`jqlang/jq:1.8`, registry defaults to `ocx.sh`) or fully qualified; a bare identifier without tag defaults to `:latest` and the written entry is explicit; binding name defaults to the repository basename, `NAME=` overrides. Example for the feature repo: `ocx add ocx.sh/pnpm/pnpm:12` writes `pnpm = "ocx.sh/pnpm/pnpm:12"`; then `ocx lock` if `--no-pull` was used. `ocx remove|rm`, `ocx update`, `ocx upgrade` exist.

## Implications for the feature

1. **Wrapper vs own logic.** Thin wrapper around the official installer is feasible and correct, but only in `OCX_INSTALL_NO_SETUP=1` mode. Default mode runs `ocx self setup`, which needs the registry at build time, edits the build user's (root's) profiles and session PATH, writes 0600 `env.*` files, and the result is per-user; none of that serves `remoteUser`. With NO_SETUP the installer gives, for free, libc/arch detection, a checksum from a different origin than GitHub, retries, mirror/CA knobs, and truncation-safe fail-closed behavior. It costs: needs `curl`|`wget`, `tar`, a sha tool, and CA certs present in the image (the feature must install them via apt/apk/dnf if missing, which is image-family specific); and the binary lands in `$OCX_HOME/symlinks/.../bin/ocx`, so the feature must `install -m 0755` it to `/usr/local/bin/ocx` (and delete the staging `OCX_HOME`) to get a normal system install. Alternative "own logic": ~15 lines (uname -m, pick `x86_64|aarch64`, libc via same probes, download `releases/download/v$V/ocx-<triple>.tar.gz`, check against `.sha256` or `dist.json`, `tar`, `install`). This has equal tool needs and loses the cross-origin checksum unless it also reads `dist.json`; recommend pinning the installer by URL (`https://setup.ocx.sh/sh/<version>`) instead of reimplementing. Alternative that removes the installer's host-tool needs entirely: always fetch the `*-musl` archive (static) with the feature's own curl, skipping libc detection. The musl binary is the same release the docs call "universal" (`docker.mdx:58`) and the package store already installs musl everywhere (`release.yml:67-73`).
2. **Base-image feasibility.** Linux x86_64/aarch64 on glibc >= ~2.34 (gnu archive) or any libc (musl archive, **[tested]** on alpine, debian-slim, busybox-musl). Alpine works with the stock BusyBox wget path (**[tested]**) but only the musl-published tools apply (`node` is glibc-only; pnpm/shfmt/jq/shellcheck ok on amd64 musl, pnpm lacks arm64 musl). Distroless/scratch cannot run a Feature at all (needs a shell to execute `install.sh`) but the ocx binary itself would run there. 32-bit and riscv/ppc/s390x are unsupported by ocx.
3. **Install location.** System-wide binary at `/usr/local/bin/ocx` (root-owned, on every user's PATH, matches the project's own devcontainer/Docker recipe) and leave `OCX_HOME` at its default `~/.ocx` per user, so root and `remoteUser` each get a private store; run `ocx pull` from `postCreateCommand` as `remoteUser` (no sudo). Do not share a root-created `OCX_HOME` with `remoteUser` (**[tested]**: permission errors until world-writable). Set `OCX_NO_UPDATE_CHECK=1` via `containerEnv` (images do) and consider `OCX_NO_CONSENT=1` plus `OCX_CONSENT_PATHS=/workspaces/*` for activation without per-prompt hooks. Do not run `ocx self setup` for the build user; if per-user shell integration is wanted, run `ocx self setup --no-modify-path` or the `eval "$(ocx --offline env --shell=bash)"` snippet as `remoteUser` after create.
4. **Toolchain wiring for the feature repo.** `ocx pull` after clone, then `ocx exec -- <cmd>` or PATH from `ocx --format json shell state | jq -r .toolchain_bin`. pnpm: `ocx add ocx.sh/pnpm/pnpm:12`; node is already pinned (glibc only). bats-core and hadolint are not in the catalog.
